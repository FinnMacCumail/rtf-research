# Research Log

## 2026-09-20 — Tuning: 3.8x prefill from one flag, and a speculative-decoding dead end ✅
- **The measurement.** Four configurations on a 9,093-token agent-shaped prompt (NetBox records, then a request to tabulate them), one server at a time, baseline re-measured in the same session rather than compared against earlier figures. Baseline 34.0 tok/s prefill / 5.0 decode; **`-b 2048 -ub 2048` → 129.7 prefill (3.8x) and 113.7 s wall (2.8x)**; `--spec-type ngram-simple` → 36.9 / 3.8 with **0 of 163 drafts accepted**; both together → 101.4 / 3.7, worse than `-ub` alone on every axis.
- **Why the batch flag matters so much.** llama.cpp only copies CPU-resident expert weights to the GPU once a microbatch is large enough to amortise the PCIe transfer. The default `-ub 512` never reaches that threshold, so every microbatch pays full freight. With 112 GB of experts in system RAM this one threshold dominates prefill — and prefill is where an agent lives: **187,272 prompt tokens against 21,825 generated** in the 12-question run. Modelled: ~155 → ~105 min, full v5 18.6 h → ~12.6 h. *Modelled, not measured* — the projection accounts for ~100% of observed wall time, which is too neat to trust.
- **The dead end I talked myself into.** `--spec-type ngram-simple` needs no draft model, costs no VRAM, and looked made for an agent that constantly echoes device names and JSON keys out of tool results. I predicted it would help. It proposed 163 drafts and accepted **zero**, costing 24% of decode. The reason is mechanical: it needs an exactly-repeating 12-token run to predict the next 48, and a table of *distinct* device names has almost none. No `--spec-ngram-*-size-n` value fixes a 0% acceptance rate. Draft-model speculation is separately impossible — `common/speculative.cpp` throws on vocab mismatch and no qwen4exp-vocab draft model exists. Written into the serve script header so it is not rediscovered.
- **Two negatives that closed off the obvious levers.** Prompt caching was *already* working: median LCP similarity **0.956**, 75 of 76 requests warm, only 2,432 of a mean 16,405-token context actually prefilled — **~85% from cache**, with the residual being genuinely new tool-result text. I had briefed a research pass on the assumption the 9k system prompt was re-read every turn; it wasn't. And **MoE CPU decode runs at ~19% of STREAM bandwidth** with no available remedy: NUMA weight mirroring is the matched fix, and `GGML_NUMA_STRATEGY_MIRROR` exists in ggml's enum *and nowhere else in the source*. Alternative runtimes are worse — KTransformers requires Ampere+ and AMX this Cascade Lake host lacks; vLLM and SGLang cannot host 112 GB on 21 GiB of VRAM at all.
- **A measurement error of my own, recorded.** The first benchmark ran ~2 hours instead of ~18 minutes because I sized the test prompt with `chars/4` and dense JSON tokenises ~1.9x worse — ~43,000 real tokens instead of the intended ~9,000, and `cache_prompt: false` made every config pay two full prefills. Killed and re-run corrected. Separately, `pkill -f` matched the very command doing the matching and aborted two consecutive cleanup commands; PIDs that appeared to "respawn" were my own shell each time.
- **Docs**: ADR-0038 gains the prefill lever under *Positive* and three new *Negative* entries; Phase 5 → Local Frontier Inference gains a Tuning section.

## 2026-09-20 — The local constraint was the context window; I spent two runs proving it wasn't ⚠️→✅
- **What the scaled run showed.** Twelve stratified questions (4 per tier, 6/6 across both data islands, full evaluator set) against the same model and hardware: at `-c 32768`, **8/12 correct with 3 questions lost to context** — 2 hard overflows and 1 *silent* truncation, which is the worse failure because the model then answers confidently from data it no longer has. At `-c 131072 --no-kv-offload`: **11/12 correct, 0 lost**, peak context 44,295 tokens. All three previously-lost questions recovered **and scored correct**; a fourth flipped wrong → correct.
- **The fix was one flag and took 20 seconds to verify.** `--no-kv-offload` moves the KV cache into system RAM — this box has **376 GB of RAM against 21 GB of VRAM**, so the scarce resource was never the one under pressure. It buys 4× context for ~37% of decode speed (11.2 → 7.0 tok/s).
- **The cost went UP, and that is the honest reading.** 60 → 88 tool calls, 82 → 155 minutes (**1.9×**), full-v5 extrapolation ~10.3 h → **~18.6 h**. The agent got slower because it stopped hitting a wall and started finishing the work. A runtime measured on a configuration that silently drops a quarter of its questions is not a runtime worth quoting — and I had quoted it.
- **Two runs wasted on the wrong layer.** Convinced that oversized tool payloads were the problem, I built a per-result size cap into the MCP wrapper. It shipped **inert**: `langchain_mcp_adapters` declares `response_format="content_and_artifact"`, so tool coroutines return a `(content, artifact)` tuple, and my `_measure_result` handled only `str`/`list` — it skipped every MCP result (three oversized results, zero cap firings). My unit test fed it a bare string, so it validated my *assumption about* the adapter rather than the adapter's contract. **A test written from the same misunderstanding as the code cannot catch that misunderstanding.** Fixed, it shipped **mis-sized**: 60,000 chars ≈ 15,000 tokens ≈ 63% of the 23,768-token working budget, which still permitted a truncation while turning a question the baseline answered in **3 calls / 141 s** into a **65-minute retry loop**.
- **The model behaved better than my guidance did.** Under the cap it never reissued an identical call until the fourth firing, decomposed the changelog by action type, and worked out that `limit` belongs *inside* `filters` — despite my error message advising a `limit` parameter that `netbox_get_changelogs(filters: dict)` does not have.
- **The lesson is ordering, not caps.** The cheap hypothesis — "is the window simply too small?" — cost 20 seconds to test and made the entire exercise unnecessary. I tested the expensive hypothesis first because I had already decided what the answer was. The user asked "if the issue is the context then shouldn't we revert?" and that one question was worth more than both runs.
- **Docs**: ADR-0038 gains a Correction block with the `≥32k` claim struck in place (original reasoning preserved); Phase 5 → Local Frontier Inference gains the 12-question comparison and the detour as a process lesson.

## 2026-09-19 — Phase 5: a 176B model ran locally and got all three questions right ✅
- **The premise that changed.** Every local model tried against this agent had failed the **simple** tier, which made model-handoff routing moot — there was nothing to hand off *from*. **Qwen3.8-Flash-Next** (`qwen4_exp`: 125B MoE, ~6B active per token, plus a **51B n-gram lookup table** — a table, not a network, so it costs memory rather than computation) went **3/3** on one v5 question per tier, including the two-hop power trace. It named `sea-dc1-esx05` / `sea-dc1-pdu03` Outlet 1, classified every decoy the reference lists correctly, and volunteered the cable's own label *"single supply - D10"* as evidence the single feed was deliberate rather than a data gap.
- **Correctness didn't separate the tiers; cost separated them by 10×.** All three scored 1.0 coverage. Simple and medium took **2 tool calls each**; advanced took **20** against a budget of 12, over 16.6 minutes. That is direct local evidence for ADR-0037's conclusion that **efficiency, not correctness, is the usable routing signal** — and it maps onto the anchor-count rule already used for GraphQL-vs-MCP routing: cheap for one named object, expensive for set-anchored multi-hop work.
- **The tuning flag beat the upgrade.** The llama.cpp checkout was 2362 commits stale, so I rebuilt it to test whether the measured ~19 GB/s bandwidth ceiling was a stale-binary artefact. It wasn't — the new build measured *flat to slightly worse*. What did move the number was a default nobody had touched: llama.cpp sets `--numa` to **disabled**, so threads straddle both NUMA nodes. `--numa isolate -t 10` gave **+47%** CPU-only and **+56%** hybrid decode (13.71 → 21.38 tok/s), lifting effective bandwidth ~19 → ~28 GB/s against a 101.5 GB/s STREAM ceiling. Thread count is counter-intuitive: `-t 10` (one node's physical cores) beats `-t 20`, and unpinned `-t 40` collapses to 5.89. Apparent per-GPU speed differences were the same artefact — an 18.00-vs-12.28 gap between identical cards shrank to 17.91-vs-16.44 once pinned.
- **Two errors of mine, recorded.** The advanced question first failed with `request (18181 tokens) exceeds the available context size (16384 tokens)` — **my** limit, chosen because quantized KV couldn't be confirmed safe on this hybrid Gated-DeltaNet architecture. At 32k it ran to 28,106 tokens and answered correctly; **≥32k is a requirement**, not a preference. Separately I had relayed third-party reports of tool-call fragility (repetition loops, malformed `<tool_call>`, premature stops) as *disqualifying*. Across 17 logged turns none of it appeared — but at the reported ~0.7%/turn rate, 24 tool calls yields **~0.17 expected failures**, so observing zero is consistent with the problem being real. The strong claim is **withdrawn, not refuted**; absence of evidence at this sample size is not evidence of absence.
- **The honest limit**: **n=1 per tier is an existence proof, not a score.** Having just corrected an over-generalisation from n=3 *models*, generalising from 3 *questions* would be the same error with less excuse. Full v5 extrapolates to ~12 h per run (~36 h at 3× replication), which is what makes the harness impractical locally — throughput, not capability.
- **Docs**: ADR-0038 added; Phase 5 → Local Frontier Inference added.

## 2026-09-19 — Phase 5 correction: the v5 "ceiling" was an artefact of testing similar models ⚠️→✅
- **The claim I got wrong.** On 2026-09-17 I concluded from three model families that the v5 set had *saturated* — 69 of 90 items solved by all three, every paired CI including zero — and recorded it in **ADR-0037** as a negative result. I went further and predicted that further model runs would be **"uninformative by construction."** Both statements were generalisations from **n=3 models of comparable strength**, and the next run falsified them.
- **What the fourth model showed.** `qwen3.5:397b-cloud` — a family distant from both deepseek and kimi — scored **0.817** (simple 0.900 / medium 0.883 / advanced 0.667) against flash 0.906, kimi 0.911, pro 0.933, and produced the **first significant results the benchmark has generated**: pro − qwen **+0.117 [+0.038, +0.196]**, kimi − qwen **+0.094 [+0.016, +0.173]**. The three mutual comparisons among flash/pro/kimi remain non-significant, exactly as before.
- **The real lesson is about saturation.** It is a property of **the models you test**, not of the questions. Adding one unrelated family moved saturation from **69/90 to 59/90** and the all-defeating core from 3 items to 2. Ten questions that looked inert — `vcpu-aggregation`, `ip-mask-mismatch`, `orphaned-cable`, `prefixes-without-vlan`, `tenant-group-size`, `vms-without-primary-ip` and four more — were discriminating all along; the measurement simply lacked the model spread to reveal it. Read a high saturation figure as a statement about your model sample, and test it with something unlike the rest before declaring a set exhausted.
- **Corrected claim**: the set resolves capability gaps of roughly **9pp and above** on 90 paired items, and cannot resolve the ~3pp between three closely-matched models. That is a sample-size limit working correctly. Separating 3pp would need roughly an order of magnitude more questions — a poor trade against testing more varied models.
- **Three reference-WORDING defects** surfaced in the same period, all found by investigating model *disagreements* rather than by any automated check: `deletion-cascade` (all three answered "7 request IDs" and were literally correct), `tenantless-instance-wide` (the NC State site is `name='MDF'`/`slug='ncsu-065'`; a model was penalised for using the display name) and `cross-estate-power-compare` (the ANSWER dropped the "data centre" scope the question set). A full 90/90 factual audit against live NetBox found **zero** factual errors — and could not have caught any of these three. An ambiguous reference produces *false* contradictions, penalising correct behaviour; it is more dangerous than a wrong question because nothing in the harness flags it.
- **Docs**: ADR-0037 revised in place with a visible Correction block (original reasoning preserved); Phase 5 → Stratified Benchmark v5 updated; Benchmarking methods rewritten on saturation and the two distinct levers (wider model spread vs harder items).

## 2026-09-17 — Phase 5 continuation: stratified 90-question benchmark (v5) & the ceiling ✅ *(superseded — see 2026-09-19)*
- **Why scale the dataset at all**: the harness ran on **six** questions, where the 95% CI on a pass rate is ≈±0.32–0.40 — wide enough to swallow any routing-sized effect — and difficulty was not an axis at all. Model-handoff routing rests on a premise never tested: *that query difficulty predicts which model should handle a query.* Testing it needs a set that resolves the effect **and** treats difficulty as principled structure.
- **The design rule that mattered**: **difficulty is the retrieval mechanism, never the subject matter** (simple = one object/one filter; medium = one join or one aggregation; advanced = ≥2 hops or absence reasoning). Had "advanced" meant "circuits questions", the benchmark would have measured topic familiarity and called it difficulty. Stratified on four axes at once — tier × answer type × domain × data island — with the binding constraint that **every tenant appears in every tier** (19/19/19 and 11/11/11), or tenant name silently becomes a proxy for difficulty. Data came from an **additive** tenant seeded beside the untouched demo instance; ground truth computed live through the agent's own **read-only** token, so a question is never unanswerable for the wrong reason.
- **The result is negative, and that is the finding.** Three model families: flash 0.906, kimi-k2.6 0.911, pro 0.933 — **every paired CI includes zero** (tightest: pro − kimi +0.022 [−0.033, +0.078]). The means hid the real diagnostic: **69 of 90 items are solved by all three models and only 3 defeat all three.** A ~77%-saturated set cannot discriminate capability, because the solved items carry no information. Recorded in **ADR-0037** rather than buried — further model runs against this set are uninformative *by construction*; raising the ceiling needs harder items, not more models.
- **What survives the ceiling is efficiency.** Tool calls separate the same three models cleanly (pro 4.93 / kimi 5.76 / flash 6.27; 76/69/66 of 90 within per-tier budget). For routing, **cost per query discriminates where correctness cannot** — pro reaches the same answers with ~21% fewer round-trips. Also surfaced three reproducible, family-independent gaps, led by an instance-wide tenant-null aggregation where all three models report the *unfiltered* total.
- **Authoring the ground truth was where most errors lived.** An audit found **four of the six existing v4 examples carried `expected_entities` their own `reference_answer` could not match** — a *perfect* answer could not score 1.0, one self-scoring 0.500 — meaning some previously-quoted entity-coverage numbers were depressed by an authoring bug, not by model behaviour. Self-match turned out to be necessary but *not sufficient*: a `"<number> <noun>"` entity breaks when a correct answer inserts a qualifier ("13 sites" misses "13 **Dunder-Mifflin** sites"), so identifiers beat synthesised counts. Absence items cannot carry entities at all — the same model phrased the same "none" answer two incompatible ways across two runs. And **`entity_coverage` is confounded with verbosity**: the most *correct* model scored *lowest* on it while writing answers 71% the length of its rival's.
- **Two harness defects had to be fixed before authoring**: the dataset loader was **create-only**, so editing the source had no effect once the dataset existed (iterating on 90 items needs a real add/update/delete reconcile); and the results reader could return before the reference-grounded correctness score landed, silently dropping the primary metric.
- **New docs**: Phase 5 page (Stratified Benchmark v5 & the Ceiling); Benchmarking methods extended (scale, stratification, **saturation as the metric that matters**, authoring rules, coverage-vs-verbosity); **ADR-0037**.

## 2026-07-29 — Phase 5 continuation: Evaluation correctness & GraphQL read path ✅
- **The completeness metric was blind to hallucination**: the Phase 5 harness scored one answer 0.9 on completeness while it hallucinated the exact figure the question asked for — "~7.7% IP utilization / 180 IPs allocated" where the verified truth was **0%** (the demo instance's 180 IPs all sit in an unrelated `172.16.0.0/24` range, none in the sites' `10.112.x` prefixes). Root cause: `completeness_judge` was fed `expected_entities`, never the `reference_answer`, which existed but was read by no evaluator.
- **Reference-grounded correctness judge** (the fix): a new evaluator fed the `reference_answer` that scores *contradiction*, not coverage. Re-scoring the stored 9-model June sweep (judge calls only, no re-runs) surfaced **9 hallucinations completeness had rated complete** and **reordered the leaderboard** — deepseek-v4-pro (0.717 completeness → 0.833 correctness) overtakes flash (0.800 → 0.583); the June "flash ≥ pro" headline was a completeness artefact. Produced the corrected `netbox-benchmark-v4` dataset. Recorded in **ADR-0033**.
- **Recreating the Cloud "agent-native" reads on community NetBox**: appraised NetBox Labs' Cloud-only Platform MCP Server (~100 tools, sandboxed "Code Mode"). Its Knowledge layer (Agent Skills) is open-source; its cross-domain *reads* map to the community GraphQL API; its governance layer is write-safety machinery irrelevant to a read-only agent. Built a **read-only `netbox_graphql` tool** (+ `netbox_graphql_schema` introspection) PRP-first in two phases; read-only enforced by `graphql-core` AST inspection; generalizes to any NetBox type via runtime schema discovery, not a fixed schema. Recorded in **ADR-0034**.
- **Measured A/B, done right**: GraphQL vs MCP-only on `v4` with the correctness judge. The site-comparison IP-allocation trap — which hallucinated a different fabricated % on *every* MCP run — scored **0.5 → 1.0 on both production models**; deepseek-v4-pro overall 0.65 → 0.883. Cost: ~2× tool calls, plus a soft-routing over-selection side-effect on one simple query. Verdict: keep GraphQL as a complementary path, not the default; per-question win robust, aggregate needs ≥3 runs (single-run variance).
- **New docs**: Phase 5 pages (Evaluating for Correctness, GraphQL Read Path); Research Methods → Benchmarking extended (completeness vs correctness); ADRs 0033–0034.
